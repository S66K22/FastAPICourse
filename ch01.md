# FastAPI + Pydantic AI: Architecture and Security Review

A compact review guide for designing an AI-backed API with clear boundaries, typed input/output, and least-privilege access.

## 1. Core idea

**A model call is not an application architecture.** A production application also needs input/output contracts, authorization, error handling, resource limits, and clear responsibility boundaries.

Think of the agent as one typed component inside the application—not as the whole application.

```text
Client
  |
  v
FastAPI route ---- request validation / authentication / HTTP response
  |
  v
Application service ---- workflow coordination / business rules / error translation
  |                 |
  v                 v
AI agent          Repository
(model, tools,    (scoped data access)
 typed output)       |
                     v
                  Database
```

Not every endpoint needs every component. Add a service, repository, or tool when it provides a useful boundary.

## 2. What each layer should do

| Layer | Main responsibility | Should generally avoid |
|---|---|---|
| **FastAPI route** | Receive HTTP requests, validate request shape, enforce/request authorization, call the service, return an HTTP response | Prompt construction mixed with SQL, broad business logic, unrestricted provider-specific response objects |
| **Pydantic models** | Define and validate data contracts | Assuming valid structure means the content is factually correct or authorized |
| **Pydantic AI agent** | Coordinate model interaction, declared tools, dependencies, and typed output | Owning all HTTP, storage, and security responsibilities |
| **Application service** | Coordinate workflow, apply business rules, handle known failures, decide what success means | Becoming a generic container for unrelated code |
| **Repository** | Read/write data and enforce data-access scope | Exposing unrestricted database access when only narrow operations are needed |
| **Tool/client** | Expose a specific operation or communicate with an external system | Holding more authority than the operation needs |
| **Security/operations controls** | Enforce identity, permissions, timeouts, rate limits, and resource budgets | Relying on prompts alone to enforce security |

### Separation-of-concerns rule

A route that validates input, constructs a prompt, calls a provider, runs SQL, and catches every exception has too many responsibilities. Move each decision to the layer that can test and enforce it.

Short code is not automatically simple code. The goal is clear boundaries, not the maximum possible number of classes.

## 3. Minimal FastAPI + Pydantic AI integration

This example demonstrates the basic flow: typed request → agent → typed result → JSON response.

```python
from typing import Literal

from fastapi import FastAPI
from pydantic import BaseModel
from pydantic_ai import Agent

app = FastAPI()


class AnalysisRequest(BaseModel):
    report: str


class AnalysisResult(BaseModel):
    summary: str
    severity: Literal["low", "medium", "high", "critical"]


agent = Agent(
    "openai:YOUR_SUPPORTED_MODEL",
    output_type=AnalysisResult,
    instructions="Analyze production incident reports.",
)


@app.post("/analyze", response_model=AnalysisResult)
async def analyze(request: AnalysisRequest) -> AnalysisResult:
    result = await agent.run(request.report)
    return result.output
```

**Setup (using `uv`):**

```bash
uv init fastapi-project
cd fastapi-project
uv add fastapi --extra standard
```

Save the Python example as `main.py`, configure the model provider and credentials using the provider's documented setup, then run:

```bash
uv run fastapi dev main.py
```

Typical local URLs:

- API endpoint: `http://127.0.0.1:8000/analyze`
- Interactive API docs: `http://127.0.0.1:8000/docs`

`YOUR_SUPPORTED_MODEL` is a placeholder; replace it with a model identifier supported by your installed Pydantic AI version and provider configuration.

### What the code means

| Code | Meaning |
|---|---|
| `app = FastAPI()` | Creates the HTTP application |
| `class AnalysisRequest(BaseModel)` | Defines the incoming request schema |
| `report: str` | Requires `report` to be a string; it does not reject an empty string by itself |
| `class AnalysisResult(BaseModel)` | Defines the result's structure |
| `Literal["low", ...]` | Restricts severity to the listed values |
| `Agent(...)` | Configures the AI agent |
| `output_type=AnalysisResult` | Requests and validates output against the declared schema |
| `@app.post("/analyze", ...)` | Registers a POST endpoint and declares its public response model |
| `request: AnalysisRequest` | Lets FastAPI parse and validate the request body |
| `await agent.run(...)` | Runs the agent asynchronously |
| `result.output` | Retrieves the agent's output after a successful run |
| `response_model=AnalysisResult` | Defines the public response schema and serialization behavior |

Example request:

```json
{
  "report": "The payment service has been unavailable for 15 minutes."
}
```

Example response (illustrative; actual model output varies):

```json
{
  "summary": "The payment service is unavailable, preventing payments.",
  "severity": "critical"
}
```

**Important:** schema validation checks structure and types; it does not prove that the model's conclusion is factually correct.

## 4. Input and output contracts

A **contract** defines what a component expects and promises.

- **Input contract:** which fields are accepted, their types, and any constraints.
- **Output contract:** which fields clients receive and their types.
- **Internal result vs public response:** these may be different models. Map internal results to a dedicated public response rather than returning provider objects wholesale.

Example request validation:

```python
from pydantic import BaseModel, Field


class AnalysisRequest(BaseModel):
    report: str = Field(min_length=1, max_length=20_000)
```

This example rejects an empty report and limits its length. Choose limits appropriate for the application.

A valid schema does not automatically ensure that text is safe, truthful, or authorized.

## 5. Failure behavior and operational limits

Decide how each failure should be handled rather than catching every exception and hiding it.

| Situation | Possible response/policy |
|---|---|
| Invalid request body | FastAPI commonly returns HTTP `422` |
| Missing/invalid authentication | HTTP `401` |
| Authenticated but not permitted | HTTP `403` |
| Rate limit exceeded | HTTP `429` |
| Upstream model timeout | Map to a suitable gateway/service error, often `504` when appropriate |
| Unexpected internal failure | HTTP `500`; do not expose secrets or stack traces to clients |
| Database write fails | Follow an explicit policy; if persistence is mandatory, do not report full success |

Useful limits include:

- Maximum request/report length
- Model timeout
- Maximum output tokens
- Maximum tool-call iterations
- Per-user rate limits
- Concurrency and cost budgets

Exact status codes and retry policies depend on the application's semantics. Do not automatically retry non-idempotent operations without considering duplicate side effects.

## 6. Security: credentials, scoped dependencies, and least privilege

**Credentials** are mechanisms used to authenticate or authorize access: passwords, API keys, access tokens, or database credentials.

Avoid giving an agent or its tools unrestricted authority when the task requires only a narrow capability.

### Risky vs safer interface

```python
# Risky design if this exposes broad administrator privileges:
agent_dependencies.db_admin
```

```python
# Better interface when it truly restricts access:
agent_dependencies.incident_reader
```

These are illustrative attribute names, not built-in Pydantic AI APIs. The name alone does not provide security. The implementation and underlying permissions must enforce the restriction.

For example:

```python
class IncidentReader:
    def get_incident(self, incident_id: str):
        # Retrieve only records the current caller/workflow may access.
        ...
```

`...` is Python's ellipsis literal, used here as a placeholder for an implementation.

A narrow reader might expose only operations such as `get_incident` or `list_recent_incidents`, rather than arbitrary SQL execution, payment modification, or record deletion.

### Two layers of protection

1. **Capability restriction:** give the agent's tools only the operations they need.
2. **Resource-level enforcement:** use database permissions and authorization checks to restrict what the underlying account can access.

A scoped wrapper is not sufficient if it secretly uses an unrestricted account and fails to enforce authorization. Use least-privilege database credentials as defense in depth.

Do not put raw credentials in prompts or accept them from ordinary user request bodies. Keep secrets in trusted server-side configuration or a secret manager.

### Trusted vs caller-supplied data

| Value | Source | Security treatment |
|---|---|---|
| Incident report | HTTP request | Untrusted input |
| User identity | Verified authentication mechanism | Trust only after verification |
| Tenant ID | Trusted authorization context | Do not trust a caller-supplied ID by itself |
| Model API key | Server configuration/secret manager | Secret; never send to the model |
| Database connection | Application infrastructure | Keep under application control |

If data is tenant-specific, enforce tenant scope in the service/repository or database policy. Do not rely on the prompt to prevent cross-tenant access.

## 7. Incidents: vocabulary

In software engineering, an **incident** is an unexpected event that disrupts or threatens a system's reliability, availability, or security.

Examples:

- Payment service is down.
- Database is unavailable.
- Login system may be compromised.
- Server is running out of memory.

An **incident report** describes what happened and may include impact, timing, symptoms, and relevant evidence. An agent can summarize or classify the report; it does not automatically fix the incident.

## 8. Diagnostic table

| Symptom | Likely cause | Corrective action |
|---|---|---|
| Route contains prompt and SQL | Responsibilities collapsed | Move workflow to a service and storage operations to a repository |
| Agent receives raw credentials or broad client | Excessive authority | Pass a scoped client/reader and enforce least privilege at the resource |
| Public response exposes provider fields | Internal and public contracts are mixed | Map to a dedicated response model |
| Model output has the right shape but is wrong | Structural validation confused with correctness | Add domain validation, grounding, checks, and appropriate human review |
| Route catches every exception | Failure policies are hidden | Handle known errors explicitly and centralize unexpected-error handling safely |

## 9. Boundary-map exercise

Before implementing an AI endpoint, answer these questions:

1. **Choose one endpoint.** What operation does it perform?
2. **Define request and response models.** What fields are required and what constraints apply?
3. **List external resources.** Model provider, database, search, identity provider, logging, etc.
4. **Separate caller values from trusted context.** Which values come from the request, and which are verified or generated by the application?
5. **Assign responsibilities.** Route, service, agent, tool/client, repository, security controls.
6. **Define failure behavior.** What happens on invalid input, authorization failure, model timeout, invalid output, or database failure?
7. **Set operational limits.** Timeouts, input/output limits, tool iterations, rate limits, and cost/concurrency limits.

Example boundary map for `POST /analyze`:

```text
Client
  |
  v
FastAPI route
  - Validate request
  - Authenticate/authorize caller
  - Call service
  |
  v
Analysis service
  - Apply business rules
  - Coordinate analysis and persistence
  - Translate known failures
  |                         |
  v                         v
Pydantic AI agent       Incident repository
  - Analyze report        - Enforce data scope
  - Return typed result   - Read/write records
                              |
                              v
                           Database
```

Not every design needs all components. If the agent only analyzes supplied text and no persistence or tools are needed, a route calling an agent directly can be reasonable for a small endpoint. Add layers when they establish useful, testable boundaries.

## 10. Review checklist

- [ ] Request and response have explicit schemas.
- [ ] The public response does not expose unnecessary provider/internal fields.
- [ ] The route does not combine unrelated HTTP, prompt, SQL, and business logic.
- [ ] The agent has only the tools and dependencies it needs.
- [ ] Authorization is enforced in application/resource code, not only in prompts.
- [ ] Secrets remain in trusted server-side configuration.
- [ ] Tenant/data scope is enforced where records are accessed.
- [ ] Model, tool, and database failures have explicit behavior.
- [ ] Timeouts, input limits, rate limits, and tool-call limits are considered.
- [ ] Tests cover validation, authorization, success, and failure paths.

## One-sentence takeaway

**FastAPI handles the HTTP boundary; Pydantic defines data contracts; Pydantic AI handles model interaction and typed results; services coordinate business workflows; repositories enforce data access; and security/operational controls limit authority and resource use.**
