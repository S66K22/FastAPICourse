# Building Your First Typed AI Agent — Review Notes

## 1. Core idea

A **typed AI agent** uses a declared schema for its output instead of returning only free-form prose. This makes the result easier for application code to validate, test, and consume.

Example use case: analyze production incident reports and return:
- A concise summary
- Severity
- Affected service, if known
- Whether immediate escalation is recommended
- Recommended actions

**Important:** A valid schema does not guarantee that the model's claims are factually correct.

---

## 2. Main components

| Component | Purpose |
|---|---|
| Pydantic `BaseModel` | Defines the structure and validates fields |
| Pydantic `Field` | Adds constraints such as minimum/maximum lengths |
| `Enum` / `StrEnum` | Restricts a field to a fixed set of values |
| Pydantic AI `Agent` | Configures and runs the AI agent |
| LLM | Analyzes the input and generates a response |
| FastAPI | Optionally exposes the agent through an HTTP API |

`StrEnum` requires Python 3.11+. For older Python versions, use a compatible `str` + `Enum` pattern.

---

## 3. Example output schema

```python
from enum import StrEnum
from pydantic import BaseModel, Field


class Severity(StrEnum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"
    CRITICAL = "critical"


class IncidentAnalysis(BaseModel):
    summary: str = Field(min_length=20, max_length=300)
    severity: Severity
    affected_service: str | None = None
    immediate_escalation: bool
    recommended_actions: list[str] = Field(min_length=1, max_length=5)
```

### What the fields mean

- `summary`: string of 20–300 characters.
- `severity`: only `low`, `medium`, `high`, or `critical`.
- `affected_service`: a string or `None`; defaults to `None`.
- `immediate_escalation`: required Boolean (`True` or `False`).
- `recommended_actions`: list containing 1–5 strings.

### Why schema design matters

The schema should describe what the application actually needs and represent uncertainty honestly.

For example, if the report does not name a service, `affected_service=None` is better than inventing a service name.

A required Boolean can force a yes/no decision when evidence is insufficient. If uncertainty is a legitimate state, consider a three-state enum:

```python
class EscalationDecision(StrEnum):
    YES = "yes"
    NO = "no"
    UNKNOWN = "unknown"
```

Use `UNKNOWN` only if it fits the application's business rules. Another option is a nullable Boolean.

## 4. Configure the agent

```python
from pydantic_ai import Agent

incident_agent = Agent(
    "openai:your-approved-model",
    output_type=IncidentAnalysis,
    instructions=(
        "Analyze production incident reports. "
        "Do not invent impact, ownership, or completed remediation."
    ),
)
```

Replace `openai:your-approved-model` with a valid model identifier supported by the installed Pydantic AI version and approved for the deployment. It is a placeholder, not a guaranteed working identifier.

### What each argument does

- Model identifier: chooses the provider/model.
- `output_type=IncidentAnalysis`: declares the structured output contract.
- `instructions`: describes the task and evidence policy.

Instructions are not a security boundary. Enforce permissions and critical business rules in application code.

---

## 5. Run asynchronously

In an asynchronous service such as an `async def` FastAPI route, prefer asynchronous execution:

```python
result = await incident_agent.run(
    "The payment API is returning HTTP 500 errors."
)
analysis = result.output
```

- `await` suspends the coroutine while waiting for the result, allowing the event loop to handle other tasks.
- `result.output` is the validated output in the API pattern used in this example; check the installed Pydantic AI version.
- Avoid calling a synchronous method such as `run_sync()` directly in an async route if it can block the event loop.
- Async execution does not make the model faster and does not remove the need for timeouts and error handling.

FastAPI and Pydantic AI have separate roles:
- Pydantic AI runs the agent.
- FastAPI exposes the service over HTTP.
- Pydantic defines and validates data models.

---

## 6. Keep model selection replaceable

The model name is configuration, not the identity of the application. Avoid scattering it across modules.

For example:

```python
import os
from pydantic_ai import Agent

model_name = os.environ["AI_MODEL"]

incident_agent = Agent(
    model_name,
    output_type=IncidentAnalysis,
    instructions=(
        "Analyze production incident reports. "
        "Do not invent impact, ownership, or completed remediation."
    ),
)
```

Deployment configuration can set `AI_MODEL` to an approved, supported identifier.

A model change should ideally leave the schema, tools, tests, and business rules unchanged. However, different models can behave differently, so evaluate changes before release.

## 7. Example: validating data without an LLM

```python
analysis = IncidentAnalysis(
    summary="The payment API is failing intermittently.",
    severity=Severity.HIGH,
    affected_service=None,
    immediate_escalation=True,
    recommended_actions=["Inspect application logs"],
)
```

This should satisfy the declared constraints.

A value such as `severity="extreme"`, a summary shorter than 20 characters, or an empty `recommended_actions` list should fail validation under this schema.

Pydantic may coerce some input types according to its validation settings. Do not assume every questionable value is rejected without checking the relevant configuration.

## 8. Five synthetic test reports

Run the agent on all five and inspect the structured object—not only the model's prose.

### Test 1 — Clear service and impact

> The payment API has returned HTTP 500 errors for 15 minutes. Approximately 20% of payment requests are failing. The incident began immediately after deployment version 2.4.1.

Inspect whether the model preserves the known impact and timing without claiming the deployment caused the failure.

### Test 2 — Missing service identity

> Several requests are failing intermittently. The affected component and number of users are not yet known.

Inspect whether the service remains unknown rather than being guessed.

### Test 3 — Severe, explicit impact

> The production authentication service is unavailable. All login attempts are failing across the organization. No workaround is available.

Inspect whether the severity and escalation recommendation are defensible, and whether the model invents a root cause.

### Test 4 — Insufficient evidence

> A monitoring alert fired once at 03:00. The alert cleared automatically. No errors or user impact have been confirmed.

Inspect whether the model exaggerates severity or recommends disruptive remediation without sufficient evidence.

### Test 5 — Conflicting evidence

> The database dashboard reports elevated latency, but the application dashboard shows normal request latency and error rates. The monitoring systems have not yet been reconciled.

Inspect whether the model preserves the conflict rather than declaring a confirmed outage.

These are synthetic examples. Some judgments, especially severity, need explicit business rules; there may not be one universally correct answer.

## 9. What to inspect in every result

| Field | Review question |
|---|---|
| `summary` | Does it preserve the facts and uncertainty? |
| `severity` | Is it defensible under the severity policy? |
| `affected_service` | Is it supported by evidence or guessed? |
| `immediate_escalation` | Is the decision justified by the reported impact? |
| `recommended_actions` | Are the actions relevant, proportionate, and safe? |

Also test provider failures, timeouts, validation failures, and any configured retry behavior. Do not silently treat a failed run as a valid assessment.

---

## 10. Three levels of correctness

| Level | What it means | Example check |
|---|---|---|
| Structural correctness | Output matches the schema | Pydantic validation |
| Semantic correctness | Values follow application rules | Business-rule checks |
| Factual correctness | Claims are supported by evidence | Evidence verification and evaluation against labeled examples |

A schema can ensure that `immediate_escalation` is a Boolean, but it cannot prove that the decision is right. A `CRITICAL` severity value is not proof that an incident is actually critical.

A successful run demonstrates that the pipeline worked for that case. It does not establish general accuracy or safety.

---

## 11. Diagnostic table

| Symptom | Likely cause | Corrective action |
|---|---|---|
| Model returns prose only | No application output contract | Declare a Pydantic output model |
| Async route calls `run_sync()` | Synchronous execution may block the event loop | Use `await agent.run(...)` |
| Model change requires rewriting code | Model selection is coupled to application logic | Configure or inject the model identifier |
| Model invents missing details | Schema or instructions encourage unsupported precision | Represent missing information and evaluate evidence |
| Valid output contains wrong claims | Schema checks structure, not truth | Add business rules, evidence checks, and systematic evaluation |

---

## 12. Production checklist

- [ ] Define the output schema before refining the prompt.
- [ ] Permit unknown or missing values where the source may be incomplete.
- [ ] Use enums and field constraints where they reflect real business rules.
- [ ] Keep model selection in configuration.
- [ ] Use async execution in asynchronous service paths.
- [ ] Handle provider errors, timeouts, and validation failures.
- [ ] Evaluate the agent on diverse and adversarial cases.
- [ ] Keep credentials outside prompts and restrict tool permissions.
- [ ] Test any model change before deployment.
- [ ] Require authorization or human approval before consequential actions.
- [ ] Log appropriate operational metrics without exposing secrets.

## Final takeaway

**Define the output contract first, configure the agent around it, keep model selection replaceable, and validate both structure and evidence.** Typed output makes an agent easier to integrate and test; it does not by itself make the agent accurate or safe.
